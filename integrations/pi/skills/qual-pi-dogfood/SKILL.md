# Qual project self-hosted pilot with PI

Qual is the **source of truth for tasks, bugs, published test specifications, externally reported attempts, and evidence**. PI is the code-executing host. Qual does not run PI, tests, CI, or models.

1. From the trusted Qual repository, use PI's built-in MCP server `qual-local`. Prefer `mcp__qual_local__work_item_search` and `work_item_get_context` for selecting work from the real `QUAL` project. Confirm the project UUID from the private handoff / `scripts/qual-pi.sh cli projects`. Do not invent or use stale UUIDs.
2. Use the MCP WorkItem version for claim/update/transition. Claiming only updates Qual's persisted state; it **does not start a job**. A `409` version conflict means refresh context before retrying.
3. Implement changes using PI's own editor/terminal after inspecting repository `AGENTS.md`, ADR, and actual source. Record a real Git commit and test command. **Phase 9:** use `work_role_entry_record` / `qual role record` to append immutable `executor` and `tester` role evidence using the **same real PI Principal**, anchored to actual Git/TestRun/Artifact references and WorkItem versions. Never invent Agent A/B/C identities. The API is an archive, not a test runner.
4. If real tests were externally executed, publish/choose the intended TestCaseVersion, bind a TestRun, and append only the actually observed Attempt. For one single-CaseVersion external run, use the scoped `scripts/qual-pi.sh cli test report -project QUAL -case-version <published-uuid> -title <run-name> -status passed|failed|blocked|skipped -note <real-observation> -request-key <stable-event-key> [-build <actual-sha>] [-work-item <same-project-WorkItem-UUID>]` to make these **two** existing API writes via one CLI command. Re-run **unchanged inputs and same key** after partial failure, never invent a new key to hide an error. This only registers real results; no tests are executed by Qual. **Never fabricate pass/fail results** or erase a failed Attempt after it passes later.
5. Send `in_progress → in_review` when ready. **Goose13 Agent-first**: with explicit project `owner_acceptance` policy and effective Credential Scope + Project Allow `work:review`, a real Agent who is the accountable owner (or assigned claimant when no owner exists) may complete autonomously with actual TestRun/Ready evidence, substantive reason, and `acknowledge_self_review=true`. The decision remains `independent=false` in immutable history; `self_review=true` does **not** by itself forbid project-authorized completion. If the policy is `independent_review`, a separate legitimate `reviewer:passed/self_review=false` is still required. No dummy identities. **The original low-scope PAT was replaced through trusted Human administration.** The current Local PI Agent has effective `work:review` in both its Credential Scope and Project Allow, verified by CLI and the reloaded MCP connection on 2026-11-02. It may self-accept eligible claimed work under the project `owner_acceptance` policy, but must never self-grant more scopes, bypass forced-independent work, or mislabel its real self-review as independent. Recheck `project_access_self` whenever credentials or policy change.
6. **Phase 13、先绑定真实 WorkItem 再留存：**在真实外部 Git Commit、实际 TestRun/Attempt 和已发布 CaseVersion/Coverage 都可回读后，使用 `scripts/qual-pi.sh cli evidence packet -project QUAL -work-item <real-uuid> -test-run <actual-uuid> -git-commit <full-existing-sha> -git-repo . -request-key <stable-event-key>`，把本地只读核验的 Git Commit 和实际 TestRun 固定历史归档为 **target_kind=work_item** 的 Ready 私有 Artifact。返回 Artifact UUID/SHA，必须在同一工作项读取和下载校验；同请求重试使用相同键和输入。该命令不执行 git commit/测试/CI，也不会生成 Reviewer/Done；无远程 Git URL 时不发明 GitHub ExternalReference。普通文件上传/下载继续使用 `scripts/qual-pi.sh cli evidence upload|download`；MCP 是轻量业务数据，不传多 MiB 二进制。
7. Use `mcp__qual_local__project_access_self` or `scripts/qual-pi.sh cli access me -project QUAL` to inspect your **real** permissions; credential Scope and project policy both apply. One PI Agent can act in multiple capacities without spawning another instance, but permission cannot be invented.
8. For a one-off true role fact, the scoped `scripts/qual-pi.sh cli role record ... -latest-version` can read the current item version once before submitting the same CAS-protected write (no automatic retry on 409). This optional shortcut removes repetitive manual `show`, but does not infer/execute tests or auto-approve. Read `work_role_entries_search` or `scripts/qual-pi.sh cli role list` for the timeline. Every entry has a true actor, work version, outcome, evidence reference and `self_review` flag; Git SHA is an externally reported reference, not automatically verified by Qual. Actual testing goes through a separate immutable TestRun/Attempt. Record discrepancies as Bugs. See `docs/pilot/phase9-single-agent.md`.

## Registration and credentials

The user registers the PI package and MCP server; this skill does **not** install them or retrieve secrets. To check state interactively use `/qual-status`, `/mcp` and `/qual-pilot`. Do not print `QUAL_TOKEN`, the locally protected Agent token file, Human credential, session cookies, secrets, or hidden prompts. Do not grant yourself any permission or modify another Principal unless your credential and Project policy explicitly contain `access:manage`. Human Workspace Admin must grant that management capability, and delegated Agents cannot propagate `access:manage`.

Canonical cross-client contract: `integrations/agent-skills/qual/SKILL.md`. This Pi-specific skill adds pilot discipline but does not replace the authoritative Qual REST/MCP contract.
